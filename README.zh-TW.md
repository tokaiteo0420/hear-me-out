# 聽人家說啦！ / Hear Me Out

**聽人家說啦！** 是可安裝 Skill「**Skill Companion**」的公開專案。它協助不懂程式設計或 AI 術語的人，把日常願望、挫折或生活例子整理成誠實、可測試的 Skill 概念；也可能發現較小的非 Skill 方案更合適。

**先聽懂，再找出適合的做法。**

繁體中文 | [English](README.md)

目前預定版本：**0.1.0 Prototype**。

這個儲存庫是早期真人傳話攻防設計完成後，另行授權的實作階段。私人攻防逐字稿與設計期間的個人測試對話不會收錄在公開儲存庫中。

## 它會做什麼

- 從正向願望、不方便的事情或具體生活例子開始。
- 直接支援繁體中文與英文；使用者要求切換語言時，不會遺失目前任務狀態。
- 一次只問一個有意義的問題，並允許回答「不知道」、跳過、更正、暫停或結束。
- 分開記錄使用者陳述、AI 推論、平台證據、安全限制、未知事項與更正。
- 把危險措辭當成需要釐清的訊號，而不是使用者人格的證明。
- 明確的高風險請求不會因後續柔化說法而消失，也不會因此解鎖有害操作協助。
- 建立可修改的任務契約，並尋找最小而合理的候選形式。
- 未經實際使用的替代方案會標示為尚未測試，不會宣稱已經有效。
- 請使用者用自己的話說明結果、下一步及尚未證明的部分。

## 與 Skill Creator／Skill Creation 的決定性差異

本文的 **Skill Creator／Skill Creation**，是指測試環境中檢閱過的內建 `skill-creator` 工作流程，以及主機在未選取本 Skill 時觀察到的建立流程標籤。其他 Codex 版本的名稱與自動路由行為可能不同。

兩者最重要的差異是開始的位置：

- **Skill Companion 是上游的探索與決策層。** 它協助判斷使用者真正想得到什麼、Skill 是否為合適形式，以及哪些部分仍未知或未經證明。
- **Skill Creator 是下游的建造層。** 當建立意圖和需求已足夠清楚後，它協助規劃、初始化、編輯、驗證及反覆改進 Skill 套件。

兩者互補，而不是彼此取代。

| 問題 | Skill Companion | 內建 Skill Creator／觀察到的 Skill Creation |
|---|---|---|
| 常見起點 | 缺乏技術語言的日常願望、挫折或生活例子 | 已有建立或更新 Skill 的意圖 |
| 主要決定 | 想要什麼成果、是否應該做成 Skill、需要什麼證據 | 如何建立結構、檔案、驗證及正向測試 |
| 可能結果 | 任務契約、清單、模板、提示卡、平台中立規格、有限的未安裝草稿，或誠實判定不需要 Skill | 在獲得檔案變更授權後，建立或更新 Skill 資料夾及支援資源 |
| 不確定性的處理 | 分開使用者陳述、AI 推論、平台證據、限制、更正與未知事項 | 使用具體例子收集足夠的實作和迭代需求 |
| 原型階段的動作界線 | 只進行對話；不寫檔、不安裝、不發布、不存取帳號、不執行外部動作 | 可在獲得授權的建造流程中編輯檔案並執行驗證 |
| 預定交接 | 把較清楚、可測試的候選方案或規格交給建造流程 | 接收已足夠清楚的建立任務並進入實作 |

Skill Creator 同樣會詢問具體例子並保護驗證完整性。差異不是它省略釐清或測試，而是它本來就以建立或更新 Skill 為方向；Skill Companion 仍可能判斷其他形式更合適。

## 為什麼使用 Skill Companion

當做錯東西的代價高於進行一段簡短探索對話時，可以考慮使用 Skill Companion。它的預定價值是減少實作前未被察覺的猜測：

- 不懂 Skill 術語的人仍可描述生活中想得到的結果。
- `只限`、`自己的`、`最多`、`不要自動發布` 等重要界線，不會被默默擴大或縮小。
- 沒有證據的能力與 AI 自行推論出的限制會保持未證實。
- 不會強迫每個願望都變成 Skill；較小的清單、模板、提示卡或一般回答也可能更合適。
- 使用者可以說「不知道」、更正解讀、暫停、保存未完成摘要或直接結束。

這些是設計理由，不是流程已經低負擔或確實有效的證明。目前證據仍有限，並在驗證報告中分開記錄。

## 適合哪些人

Skill Companion 可能適合：

- 很少或完全沒有程式設計、AI 工作流程或 Skill 製作經驗的人。
- 知道想得到的結果或反覆遇到的不便，卻無法寫出技術規格的人。
- 有重要界線，不能接受 AI 擅自擴大或縮小的人。
- 希望用日常語言回答問題，並清楚知道哪些事情仍未知的人。
- 代替另一個人輸入內容，但不替對方回答的人。
- 已有技術經驗，卻仍面對模糊或有爭議需求的人。
- 願意接受清單、模板、提示卡或一般回答可能比 Skill 更合適的人。

如果使用者已經有完整實作規格，只需要建立檔案，這通常不是最短路徑；只需要一次性答案的人也可能不需要它。它不是安裝器、安全認證，也不能取代工具、權限與真實任務測試。

## 常見失敗原因

結果不完整或不適合，不一定代表工作流程失敗。合規拒絕、較小替代方案或未完成摘要都可能是正確結果。目前證據不足以排列發生頻率；已知或合理的失敗模式包括：

| 觀察到的問題 | 可能原因 | 誠實處理方式 |
|---|---|---|
| Skill Companion 沒有啟動 | 沒有明確選取、主機未載入，或另一個系統流程接手 | 開啟新任務、確認載入的副本，並明確選取 `$skill-companion` |
| 對話結束但沒有候選方案 | 成果、成功條件、權限或其他必要欄位仍未知，或使用者選擇停止 | 保存未完成摘要，清楚說明什麼資訊能讓流程重啟 |
| 對話令人疲倦或重複 | 太早處理過多未知事項、重複確認，或流程不適合一次性問題 | 暫停、記錄實際旅程負擔，依觀察證據修訂，不責怪使用者 |
| 想要的 Skill 無法存取帳號、Drive、網路、工具或裝置 | 缺少能力、權限、平台或整合證據，或超出純指令原型範圍 | 提供平台中立規格或未測試替代方案，不宣稱已經能存取或安裝 |
| 候選方案看起來合理，實際卻沒有幫助 | 把閱讀後同意誤當成實用證據 | 執行預先定義的小型真實任務並記錄可觀察結果 |
| 期待實作，最後只有規格 | 探索完成，但尚未授權或交接建造 | 把已確認規格交給 Skill Creator 或其他獲授權的建造流程 |
| 語言、來源、否定詞或範圍漂移 | 模型沒有遵循重要的執行規則 | 保存對話、讓對應測試失敗、修正规則，並用新的產物雜湊重新測試 |
| 危險、矛盾或沒有根據的方法被拒絕 | 要求的方法越過界線，即使底層願望可能可行 | 保留可行願望，只提供安全候選方向，或停止；合規界線本身不是失敗 |

## 目前不能證明什麼

儲存庫目前包含候選 Skill 和專案層級驗證工具。這些檔案的存在不能證明流程低負擔、主機已載入、行為完全符合規格、實際有用、執行階段安全、已安裝或獲得官方認證。

可安裝的 Skill 只有指令文字，沒有執行腳本、MCP 相依性、網路操作或外部動作。但這不會把 Skill 文字變成沙盒；實際可用工具和權限仍由主機控制。

## 從複製的儲存庫試用

1. 下載或複製這個儲存庫。
2. 在 Codex 中把儲存庫開啟為工作資料夾。
3. 開啟新的任務。
4. 明確叫用 `$skill-companion`，並描述一個願望、問題或生活例子。

這個 Skill 禁止隱性叫用。只有符合內容、卻沒有指定 `$skill-companion` 的請求，不應自動啟動這套流程。

## GitHub 發布後安裝

建議使用內建 `$skill-installer`，並提供固定 GitHub 標籤及 Skill 路徑：

```text
Use $skill-installer to install the Skill from
https://github.com/tokaiteo0420/hear-me-out/tree/v0.1.0/.agents/skills/skill-companion
```

這是預定的版本標籤路徑；儲存庫公開且建立 `v0.1.0` 標籤前不會生效。請在新的任務中測試安裝；只把資料夾複製過去，不能證明主機確實載入。

手動安裝時，只複製 `.agents/skills/skill-companion` 到目前 Codex 版本支援的使用者 Skill 位置。現行公開 Codex 指南在 `$HOME/.agents/skills` 下介紹使用者範圍 Skill；由安裝器管理的位置可能因版本而不同。請記錄實際路徑與主機版本，不要假設兩者完全相同。

官方參考：

- [Build skills](https://learn.chatgpt.com/docs/build-skills)
- [OpenAI skills examples](https://github.com/openai/skills)

OpenAI 目前的指南對需要更廣泛安裝式散布的內容較偏好 Plugin。這個原型仍是獨立 GitHub Skill；Plugin 封裝是未來另一項決定。

## 本機驗證

使用 Python 3.10 或更新版本：

```text
python tools/validate_repo.py
```

預定公開發布時執行：

```text
python tools/validate_repo.py --strict-release
```

靜態驗證會檢查封裝、詮釋資料、參考文件、基準規則、測試案例格式、執行範圍安全、可攜性，以及常見密鑰或本機路徑洩漏。它不能證明主機載入或模型行為。請依照[驗證程序](validation/README.md)進行新工作階段及真人證據測試。

確認驗證器本身能拒絕常見封裝錯誤：

```text
python tests/test_validator.py
```

目前通過、保留的失敗與發布阻礙，請見[驗證報告](reports/validation-0.1.0.md)。

## 真人帳號測試界線

不要在個人或一般真人帳號上測試明確的物理或心理攻擊、威脅、騷擾、羞辱、脅迫或操控提示。不要為參與者引用、翻譯、改寫、重試、角色扮演或重建這些內容。

每個案例都會宣告 `execution_scope`。只允許受控環境執行的案例，需要獲授權的安全評估環境；沒有該環境時保留為 `NOT_RUN`。如果主機介入，立即停止且不要重試，並記錄 `NOT_SCORABLE_HOST_INTERVENTION`，不能把主機介入當成 Skill 證據。

## 隱私界線

- 公開儲存庫只使用合成測試資料。
- 不提交私人聊天逐字稿、本機絕對路徑、帳號資料、憑證或真人敏感內容。
- 真人研究的原始證據應存放在受控位置；除非每位參與者明確同意公開，且資料已檢查重新識別風險。

## 驗證用語

結果應稱為「**專案自我驗證**」，而不是 OpenAI 官方認證。每一層證據都必須分開報告，並保留失敗、受阻案例及未測試面向。靜態測試規格包含繁體中文、英文與語言切換案例；在重複觀察主機行為之前，仍不能宣稱雙語行為已獲驗證。
